# 軟體設計文件第 1 版（SDD v1）

## 1. 文件目的、範圍與基準

本文件說明「校園社團活動與場地智慧管理平台」0728–0729 介面重構的畫面責任、互動、資料、狀態、錯誤、權限與驗證方式。核心範圍採用 BASELINE-2026-0722-V1 的 FR-01～FR-07、0720 的 UC-01～UC-04，以及 0727 的類別、循序與狀態模型。FR-08～FR-10 只保留為原型示範與待確認事項，不宣稱為正式完成需求。

目前實作基準為 Git 提交 `59fa6ff` 後的 0728–0729 工作版本。前端資料保存在瀏覽器記憶體，Java API 資料保存在行程記憶體，重新載入或重啟後會清除。

## 2. 三個核心任務

| 任務 | 角色 | 起點 | 主要結果 | 替代／錯誤 |
| --- | --- | --- | --- | --- |
| TF-01 建立活動申請 | 社團幹部 | 建立申請表 | revision=1、待審核 | 必填與時間錯誤不建立資料 |
| TF-02 處理場地衝突 | 社團幹部 | 已載入匿名測試資料 | 修改後成功待審核 | 重疊時拒絕；相鄰時段允許 |
| TF-03 補件與審核 | 課外活動組、社團幹部 | 待審核申請 | 待補件→待審核→已核准 | 缺原因拒絕；取消修改維持待補件；非法回轉拒絕 |

詳細步驟見 [task_flows.md](task_flows.md)，畫面移動見 [screen_flow.png](screen_flow.png)。

## 3. 資訊架構與畫面責任

系統依角色目標分成活動申請、行政審核、場地資訊、活動資訊與原型驗證五個內容群組。畫面不直接複製資料表，而只呈現完成任務所需資料。完整資訊架構見 [information_architecture.md](information_architecture.md)，畫面清單見 [screen_inventory.md](screen_inventory.md)。

| 邊界／元件 | 責任 | 不負責 |
| --- | --- | --- |
| Prototype／ApplicationFormBoundary | 收集輸入、顯示驗證與送出狀態、呈現我的申請 | 不決定未確認業務規則 |
| ReviewCenterBoundary | 顯示待審核詳情、收集審核決定與原因 | 不允許非待審核資料再次審核 |
| ApplicationCards | 顯示狀態、版本與原因；提供待補件入口 | 不修改非待補件申請 |
| prototype-domain.mjs | 驗證輸入、判斷衝突、審核轉移與重送資格 | 不保存資料或處理身分驗證 |
| Java ApplicationService | 建立、查詢、審核、補件重送及狀態守衛 | 不提供正式資料持久化或外部通知 |

## 4. 互動與狀態設計

送出申請與保存審核結果時，介面先顯示處理中訊息並暫停相關欄位與按鈕，避免重複提交。成功後顯示具體狀態；失敗時保留正確輸入並提供原因與下一步。

介面定義正常、空白、載入、錯誤、停用與權限不足六類狀態，詳見 [ui_state_specification.md](ui_state_specification.md)。權限不足目前是可操作的原型狀態，用來驗證說明與恢復方式；正式系統仍須由伺服端驗證身分與角色。

## 5. 資料與狀態

| 資料 | 來源 | 使用位置 | 驗證／限制 |
| --- | --- | --- | --- |
| activityName | 使用者輸入 | 表單、申請卡、審核、活動查詢 | 必填 |
| date、startTime、endTime | 使用者輸入 | 表單、場地衝突、行程 | 必填；endTime 必須晚於 startTime |
| venue | 使用者輸入／正式來源待確認 | 表單、衝突、場地與活動查詢 | 必填；同場地同日半開區間不可重疊 |
| status | 系統狀態 | 全角色畫面 | 待審核、待補件、已核准、已退回 |
| reviewNote | 課外活動組輸入 | 補件原因與審核說明 | 待補件或已退回時必填 |
| revision | 系統計算 | 我的申請、審核中心 | 新建為 1；待補件重送 +1 |

已核准、待補件或已退回資料不可再次執行審核更新；撤銷核准規則確認前，系統拒絕未定義回轉。

## 6. 錯誤、權限與無障礙

欄位錯誤使用 `aria-invalid` 與 `aria-describedby` 關聯具體說明；整體錯誤使用警示語意，正常與載入回饋使用狀態語意。狀態不只依顏色表達，所有原生控制項具鍵盤焦點樣式，減少動態偏好時停止持續動畫。完整檢核見 [accessibility_check.md](accessibility_check.md)。

正式系統的權限控制不得只依賴角色按鈕或隱藏介面；執行層仍須在 8/3 架構設計中確認身分、授權與直接 API 存取的阻擋方式。
